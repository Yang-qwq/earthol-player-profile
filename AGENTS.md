# AGENTS.md

Single Cloudflare Worker (Hono SSR) for player-profile pages, with a built-in **admin panel** and **en/zh i18n**. D1 (data) + KV (sessions, rate limits, profile cache, settings cache) + static assets. Optional R2 (only used for avatar uploads; enabled by binding an `R2` bucket — see the storage bullet below). No test suite or linter configured.

## Commands
- `npm run dev` — runs the full `build` (CSS **and** vendor bundles) then `wrangler dev` on port 8787. Local D1 starts **empty**: run `npm run db:init` once first, or every query fails until the tables exist.
- `npm run build` / `build:css` / `build:vendor` — `build:css` runs the Tailwind CLI; `build:vendor` runs `scripts/build-vendor.mjs`, which copies the pinned `htmx.org` from `node_modules` to `public/vendor/htmx.min.js` and bundles the local CodeMirror build to `public/vendor/codemirror.js`. Both bundles share the `/vendor/*` route prefix and the generated, gitignored `public/vendor/` directory (no runtime CDN for either). `build` runs both and **must run before `wrangler dev`/`wrangler deploy`** when invoked directly.
- `npm run typecheck` — the only automated verification (`tsc --noEmit`; there is no test suite or linter). Run it after every change.
- `npm run db:init` / `db:init:remote` — apply the single `schema.sql` to D1 (local / remote).
- `npm run db:migrate` / `db:migrate:remote` — apply pending files from `migrations/` to an **existing** DB (local / remote) via `wrangler d1 migrations apply`; applied files are tracked in the `d1_migrations` table, so each runs exactly once. Fresh installs only need `db:init` (the full schema already includes every migration).
- `npm run watch:css` — Tailwind in watch mode.
- Reset local DB: delete `.wrangler/state` then re-run `npm run db:init`.
- **Throwaway DB for manual checks** (leaves `.wrangler/state` untouched): start with `wrangler dev --port 8791 --persist-to <tmpdir>` and seed with `wrangler d1 execute <db> --local --persist-to <tmpdir> --file=./schema.sql` then a seed file. Seed **before** starting the server — a write made from another process is not reliably visible to an already-running `wrangler dev` (observed with `wrangler kv key put`). Magic-link sign-in works locally: `POST /auth/email` prints the link to the dev log (console mailer).

## Non-obvious wiring
- **JSX files must be `.tsx`.** A `.ts` file containing JSX fails typecheck with misleading "Unterminated regular expression literal" errors. `src/app.tsx` and all of `src/views/*.tsx` are TSX; in `src/routes/` only `health.ts` and `language.ts` are plain TS (`api.tsx` is TSX solely because the follow toggle returns a JSX fragment). `src/lib/` is mostly `.ts` — `blocks.tsx` is the exception, as is `src/middleware/runtime.tsx`.
- **`.field` is a pill, and a `<textarea>` must not be one.** The `.field` component class uses `rounded-full`, which is right for single-line `<input>`/`<select>` but draws a stadium on a tall `<textarea>` (the top/bottom arcs bulge into the text). That is handled once, by the unlayered `textarea.field { border-radius: 1rem }` rule in `src/styles/app.css` — do **not** re-add a per-element `rounded-2xl` override on a textarea (that per-element patch is what kept getting forgotten); the stylesheet is the single owner. A new textarea just needs `class="field …"`.
- **Icons are Material Symbols, not inline SVG.** Render `<span class="material-symbols-outlined" aria-hidden="true">icon_name</span>` (font loaded from Google Fonts in `src/views/layout.tsx`, base class in `src/styles/app.css`). Don't hand-write SVG paths; Google Fonts already allows the required CSP sources.
- **CSP uses a per-request nonce** (no `'unsafe-inline'` for scripts). `secureHeaders` in `src/app.tsx` uses Hono's `NONCE` handler, which stores the value at `c.get('secureHeadersNonce')`; views thread it down as the `nonce` prop and every inline `<script>` must carry `nonce={nonce}` (see `src/views/layout.tsx` / `src/views/profile.tsx`). External scripts are allowed by host (`https://unpkg.com`, still needed for the lazily-loaded `qrcode-generator` in the profile share card). New inline scripts without the nonce are blocked in the browser. `imgSrc` allows any `https:` host (plus `'self'`/`data:`) — that is what lets avatar/gallery URLs point off-origin; `styleSrc` allows inline styles, which is why the admin custom CSS needs no nonce.
- `src/app.tsx` mounts routers in order: health, api, language (`/language/:code`), auth, onboarding, dashboard, admin (`/admin*`), files (`/files/*`), then `publicRoutes` last. `publicRoutes` owns the `GET /:username` catch-all, so **register any new top-level route in a router mounted before it**.
- Global middleware in `src/app.tsx`, in order: `resolveLocale` (sets `locale` + `t`) → `loadUser` (sets `user`, `csrfToken`, `isAdmin`) → `loadRuntime` (`src/middleware/runtime.tsx`: loads settings, sets `appName`, enforces maintenance mode) → `csrfProtection`. Handlers read these via `c.get('locale'|'t'|'user'|'isAdmin'|'settings'|'appName')`.
- **CSRF**: every POST/PUT/PATCH/DELETE needs form field `_csrf` equal to the `csrf` cookie (double-submit, `src/lib/csrf.ts`). Handlers may call `c.req.parseBody()` again — Hono caches the parsed body.
- Session cookie is `sid`, HttpOnly, KV keyed by SHA-256 of the token (`src/lib/session.ts`).
- **Profile cache**: anonymous `public` profiles are cached in KV as `profile:html:<locale>:<username>` (300s) in `src/lib/profile-cache.ts`. Each handle has up to three cached pages — the profile itself plus its followers/following list pages (`:followers` / `:following` suffixes; see the Follows bullet) — and keys are **locale-scoped** (rendered HTML depends on language), so `invalidateProfiles()` deletes every variant in every locale. Any profile/fields mutation **must** call `invalidateProfiles()` (already wired in `src/routes/dashboard.tsx`). Logged-in viewers are never served cache. Cacheable HTML is rendered with `NONCE_PLACEHOLDER` and `withNonce()` swaps in the live request nonce on every serve, because the CSP nonce is per-request and a baked-in one would block all cached inline scripts.
- **Fields (key/value pairs)**: `POST /dashboard/fields` replaces the whole list on each submit: rows with both parts empty are dropped, a half-empty row → `error=invalid_field`, >20 rows → `error=too_many_fields`, lengths clamped to 40/300, and **values are never URL-validated or normalized**. `src/views/profile.tsx` renders them as **one card** (`data-fields`) that is a section of the profile's ordered card list — its position among the blocks comes from `profile_layout.fields_position` (see the Profile blocks bullet). A value passing `isSafeUrl` becomes an `<a>` and everything else is escaped plain text.
- **Tags (categorized chips)**: admin-managed `tag_categories` (name + whitelisted color id from `src/lib/tags.ts` — full Tailwind class strings live there so the v4 scan keeps them) and per-user `user_tags` free-text values joined to a category. Admin CRUD at `/admin/tags/{add,update,remove}` (name unique case-insensitively; deleting a category cascades user tags and calls `invalidateAllProfiles()` — KV-list prefix purge, since one change affects unknown profiles). Users replace their whole tag list via `POST /dashboard/tags` (≤20 tags, value ≤40 chars, `category_id` must exist), mirroring the fields replace-on-submit pattern; `src/views/profile.tsx` renders chips as `category_name + value`. Each row also submits a `hidden` flag (paired hidden input keeps the arrays index-aligned, toggled by `TAG_HIDDEN_SCRIPT`). **Hidden tags** (`user_tags.hidden`) are shown on `GET /:username` to the **owner only** — the audience is deliberately *not* inferred from a viewer's tag values, because matching on them lets any signed-in user probe for a tag by setting it themselves. `hidden` is an owner-side display layer, not a secrecy primitive, and `same_tag` block audiences (below) are the supported way to target "people like me". They are excluded from `GET /api/tag-suggestions` (autocomplete, auth-required).
- **Profile blocks (modular profile)**: each user assembles an ordered list of blocks shown on `GET /:username`. The `profile_blocks` table (`migrations/0003_create_profile_blocks.sql`, mirrored in `schema.sql`) holds `kind` (`text` | `gallery`), `title`, `body`, `items`, `visibility`, and `sort_order`; the FK cascades with the user, and the CHECK constraints make the table itself reject an unknown `kind`/`visibility`, a `text` row without a body, and a `gallery` row without items. **The new audience rules deliberately live in satellites, not on this table** — see below. `required_tag` / `min_follow_days` are legacy columns: `migrations/0004` folded their values into `profile_block_rules` and cleared them, and nothing reads or writes them (SQLite cannot drop a column without a one-shot rebuild).
  - Audience refinement: each block carries a base `visibility` **plus** optional conditions, stored as a 1:1 satellite row in `profile_block_rules` (`block_id` PK, cascades) and explicit allow/deny rows in `profile_block_viewers`. All conditions are **ANDed** in `canViewBlock`: `relation` (`RELATIONS`: `followers` = the viewer follows the owner, `following` = the owner follows the viewer, `mutual` = both — this is where the relational audiences live, as a rule rather than a `visibility` literal); `requiredTags` (matched `any`/`all` via `tagMatch`) and `excludedTags` (any single hit denies); `allowUserIds`/`denyUserIds` (grouped by `groupViewerLists`, deny winning over an overlapping allow); `minFollowDays` (from `follows.created_at`, 0 = any follower) and `minAccountAgeDays` (from `users.created_at`); and a `visibleFrom`/`visibleUntil` time window. There is **no top-level OR** and no negation beyond the deny/exclude lists — each list is an any-of test internally. The missing OR is a deliberate, recorded trade-off (2026-10): OR under this model needs grouped/nested conditions, a new storage shape, and a much bigger dashboard editor, owners can approximate it today with duplicate blocks (one per branch) or the explicit allow list, and no user demand has surfaced — **out of scope short-term; do not add casually**. `listProfileBlocks` LEFT JOINs the satellite and flattens it onto the row as `rule_*`, so the public render path stays one query. Every condition, and every audience wider than `public`, is viewer- or time-dependent, so `isViewerIndependent` returns false and keeps the block out of the shared anonymous KV cache (`cacheableBlocks` in `src/lib/blocks.tsx` takes the grouped viewer lists too, because a listed user must never be baked into the shared copy).
  - The dashboard editor (`BlockEditorRow` in `src/views/dashboard.tsx`) exposes every field (audience, follow relation, tag lists, both age gates, the time window, and the allow/deny lists), arranged as four labelled sub-sections — follow & account, tags, time window, specific people (`data-rule-group`) — so each `sm:grid-cols-3`/`sm:grid-cols-2` row holds a related set with no orphan cell; the username picker is backed by `GET /api/user-suggestions` (auth-required, IP rate-limited, `private` profiles excluded); the route validates them strictly (reject, never coerce) before `replaceProfileBlocks` re-normalises. `src/db/queries.ts` owns `listProfileBlocks`/`replaceProfileBlocks` (replace-on-submit, mirroring fields/tags; the `DELETE` cascades the rule + viewer rows away first, and ids missing from `users` are dropped before the insert so the FK can never fail) plus `listBlockViewers`/`searchUserSuggestions`/`resolveUsernames`, and `BLOCK_LIMITS` (20 blocks, title 120, body 4000, gallery 12 items × 500 chars, 10 tags per list, 50 listed users, 3650-day caps) applied by clamp-and-drop, so a hostile post can only ever produce in-range rows; gallery `items` is stored as a canonical JSON array of strings. **Audiences are explicit and shared**: `src/lib/audience.ts` exports `AUDIENCES` (`public` | `users` | `same_tag` | `self`), `RELATIONS` (`followers` | `following` | `mutual`), the pure predicate `canViewBlock(visibility, conditions, ctx)` (the owner wins unconditionally; an **unknown** visibility is closed to every non-owner), `normaliseTagValue(s)`, `conditionsOfRow(row, lists)`/`meetsMinFollowDays`/`meetsMinAccountAgeDays`/`groupViewerLists` and `isViewerIndependent(visibility, conditions)` — true only for a `public` block with no conditions at all (a time window alone disqualifies it). `same_tag` means "shares at least one tag value with the profiled user" (normalised, case-insensitive); that makes it a membership oracle by construction (a signed-in viewer can set their own tags to probe), an accepted trade-off for a user-chosen audience rather than a secrecy primitive — the explicit allow list is the non-enumerable alternative. Editing is `POST /dashboard/blocks` (**not** the profile form): values outside the known enums are **rejected** (`?error=invalid_block`, `?error=unknown_block_user`), never coerced — coercing an audience would silently widen it to `public`, the widest audience there is. Any block mutation calls `invalidateProfiles()`.
  - Rendering lives in `src/lib/blocks.tsx`, the single `ProfileBlockRow` → markup module: text bodies are **MFM**, rendered through the same whitelisted integrator as the bio (`renderMfm` in `src/lib/mfm.ts` — all text escaped, links http(s) only, `$[…]` styling from its fixed allow-list; a body that fails to parse falls back to escaped plain text), gallery items are parsed defensively (an unparsable or non-array value renders nothing) and an item only ever becomes an `<img src>` when `isSafeUrl` accepts it — anything else is dropped from the DOM entirely rather than escaped into an attribute. The **cacheable anonymous path filters through `cacheableBlocks()`**, which keeps only rows passing `isViewerIndependent`: an explicit filter rather than relying on anonymous viewers incidentally failing every other audience, so a later widening of `canViewBlock` cannot poison the shared copy. An empty block list renders nothing at all (no shell, no layout shift), and the owner additionally sees a per-block audience marker.
  - **The profile is a list of independent cards**: `ProfileBlockCard` renders one block as its own `card` (`data-block`) *outside* the identity card, and `src/views/profile.tsx` composes the identity card first, then the blocks interleaved with the key/value fields card at `profile_layout.fields_position` (`getProfileLayout`/`setProfileLayout` in `src/db/queries.ts`; the table comes from the idempotent `migrations/0005`). That position counts **all** of the owner's blocks, so `routes/public.tsx` re-maps it onto each viewer's visible subset by counting the visible blocks that precede the anchor — a block a viewer cannot see never pushes the fields card further down. The Blocks editor (`src/views/dashboard.tsx`) lists the blocks **plus one non-removable `slot=fields` row** (`FieldsSlotRow` — dashed border, only the up/down arrows, no remove button, its rows edited on `/dashboard/fields`); the route walks the submitted `slot` array with a separate block cursor, so it reads the row order without the fields row disturbing the index-aligned block arrays, and stores how many surviving blocks precede it. `[data-block-row]` marks real block rows, which is what `BLOCK_EDITOR_SCRIPT` counts (so the fields row can never consume a block slot or hide the "no blocks yet" message).
- **Profile** visibility (the `users.visibility` column — distinct from a block's audience): `private` → 404 for non-owners; `unlisted` → renders with `noindex`, never cached; `public` → cacheable.
- **Profile share (QR + NFC)**: `src/views/profile.tsx` renders a share card for every viewer plus an inline `SHARE_SCRIPT`. The script lazy-injects `qrcode-generator` from `https://unpkg.com` (already CSP-allowed via `scriptSrc` in `src/app.tsx`) only when the user asks for a QR, draws the profile URL as an SVG/PNG, and writes it to an NFC tag via WebNFC (`recordType: 'url'`, HTTPS-only). The URL comes from `canonical` (`APP_URL` + handle), so it is absolute in cached anonymous HTML. UI strings are passed into the script as a JSON literal (locale-agnostic; all i18n lives in `src/i18n/`).
- **Follows**: the `follows` table is a directed edge (`follower_id` → `following_id`, composite PK, both FKs cascade, `CHECK follower_id <> following_id`); queries `isFollowing`/`follow` (idempotent `INSERT OR IGNORE`)/`unfollow`/`countFollowers`/`countFollowing`/`listFollowers`/`listFollowing`/`listFollowingIds` live in `src/db/queries.ts` and `deleteUser` purges both edge directions. `POST /api/follow/:username` (`src/routes/api.tsx` — the reason that file is TSX) toggles the edge: auth-gated, global CSRF applies, per-user KV rate limit `follow:<userId>` (30/h), then `invalidateProfiles([target.username, viewer.username])` — the edge touches *two* profiles (the target's follower count and the viewer's following count, each baked into the other's cached pages), so both handles are purged. It returns a fresh `FollowControl` fragment (`src/views/profile.tsx`, exported so the route can render it) on `HX-Request` and a redirect back to the profile otherwise (mirrors `renderTotpCard`/`totpGoto`). `FollowControl` renders three variants: owner → "Edit profile" link to `/dashboard`; logged-in non-owner → htmx follow/unfollow toggle form (hidden `_csrf`, `hx-target="closest [data-follow-control]"`, native POST fallback); anonymous → Follow linking to `/login?next=/<handle>`. The profile header shows a `FollowStats` row (both counts, each linking to the list page) and the two **follow list pages** — `GET /:username/followers` and `GET /:username/following` (`src/routes/public.tsx` `followListPage` + `src/views/follows.tsx` `FollowList`) — list the edges newest-first (capped at 100) with a per-row `FollowControl` for signed-in viewers (one batched `listFollowingIds` for the row states; the viewer's own row shows no toggle). **Privacy**: counts and lists exclude `visibility = 'private'` users (like tag suggestions — private profiles never leak into public follow data) and require a claimed `username`; both counts are attributes of the profiled user, so the stats row is **viewer-independent** and safe in cached anonymous HTML. The list pages are cached as their own profile-HTML variants (`:followers` / `:following` suffixes — see the Profile cache bullet) with the same `cacheable = !viewer && public` rule, so they honor `private` (404) and `unlisted` (`noindex`, uncached) like the profile itself.
- **Reports & bans (moderation)**: `migrations/0006_moderation.sql` (mirrored in `schema.sql`) adds `reports` (one row per user report, `status` open/resolved/dismissed), `user_bans` (one row per account, replaced on re-ban; `expires_at NULL` = permanent, `revoked_at` = lifted), the append-only `moderation_actions` audit log, and `report_receipts` (moderator replies to the reporter). The migration is re-runnable (`CREATE ... IF NOT EXISTS`, `INSERT OR IGNORE` for the new `report`/`suspended`/`moderation`/`reports` reserved handles). The allowed report reasons live in `src/lib/moderation.ts` (`REPORT_REASONS`, with `REPORT_REASON_KEYS`/`REPORT_STATUS_KEYS` for i18n) rather than in a SQL CHECK, so adding one stays an app-only change — widening a CHECK would need a table rebuild, which a re-runnable migration cannot contain. Users report from the profile menu (`GET/POST /report/:username`, `src/routes/moderation.tsx`, requires auth, `visibility=private` 404s like the profile itself, self/ already-banned targets are blocked, one open report per reporter/target is deduped, and posts are rate-limited per user + IP). Every ban is enforced in four places: `loadUser` reads `getActiveBan` into `isBanned` on every authenticated request; `enforceBan` (mounted after `loadUser`, before `loadRuntime`) redirects a banned session to `/suspended` (HX requests get 403) while allowing only the notice, sign-out, language switching, health, `/files/*`, and static assets; `/:username` + the follow-list pages check `getActiveBan` **before** the KV cache (owner → `/suspended`, anonymous/regular viewers → 404, admins get an uncached `noindex` preview with a banner on the profile); and all three sign-in flows re-check after authentication (TOTP only after a valid code, so suspension cannot be probed). Bans revoke sessions via the `session:user:<userId>:<hash>` reverse index (`revokeUserSessions` in `src/lib/session.ts`; pre-existing sessions without an index are still stopped by `enforceBan`) and purge every cached profile (`invalidateAllProfiles`, because follower lists/tag suggestions embed the account). Banned accounts are excluded from `listFollowers`/`listFollowing`/both counts, `listTagSuggestions`, `searchUserSuggestions`, `listUsernames` (sitemap) and the public follow API; `/files/*` also refuses media whose key owner (`avatars|gallery/<userId>/…`) is banned; admins can still find them in `searchUsers`, which returns `is_banned` for the badge. The console sidebar exposes reports as its own **top-level** module (`src/views/layout.tsx` `ConsoleShell`): a Reports group whose second level holds the reporter inbox (`/reports`, 用户版) and, for admins, the moderation queue (`/admin/moderation`, 管理员版). Moderation is filtered out of the Admin submenu (`ADMIN_SECTIONS.filter(...)`) so there is exactly one entry point; the registry keeps the entry for page titles and `ADMIN_SECTION_PATH`. `/reports` (`src/routes/reports.tsx` + `src/views/reports.tsx`) lists the signed-in user's own reports, their state, their submitted note, and every moderator receipt, and marks those receipts read on render. **Receipts** live in `report_receipts` (`migrations/0006_moderation.sql`, mirrored in `schema.sql`; one report can receive several, cascading with the report, `admin_id` nulled on deletion, `read_at` drives the unread badge). `POST /admin/moderation/reports/:id/status` accepts an optional `receipt` text: it is stored as a receipt and logged as a `receipt` action (visible to the reporter, unlike the internal `note`); a status log row is written only when the state actually changes. `countUnreadReceipts` feeds the Reports badge from `renderDashboard` and `renderAdmin`. The admin page is `/admin/moderation` (`src/lib/admin-nav.ts`, `renderAdmin` loads reports/bans/history only for that section): report filters `?status=`, per-report status + internal note + receipt, a ban card opened from `?ban=<userId>` (also linked from `/admin/users`), unban, and a 50-row action log. `POST /admin/moderation/ban` rejects invalid reason/duration, self-bans and admin targets (DB flag **or** `ADMIN_EMAILS`), then upserts the ban, resolves every open report against the target, logs a `ban` action, revokes sessions and purges the cache; `unban` marks `revoked_at` and logs; report changes log `report_<status>`. The owner-facing notice is `GET /suspended` (`src/views/suspended.tsx`), and the banned login attempts land on `/login?error=banned` (`auth.err.banned`).
- **Optional R2 storage (avatar uploads)**: `src/lib/storage.ts` is the only module that touches `env.R2`; `storageEnabled(env)` gates everything. `Env.R2` is optional and **every** code path is gated on it: with no `r2_buckets` binding (absent or commented out in `wrangler.jsonc`) the upload UI is hidden and nothing else changes — the README documents enabling it. When bound, the profile form is `multipart/form-data` and the avatar-URL row (`uploadEnabled` prop) renders a visible Upload button beside the URL field; clicking it (delegated `AVATAR_FILE_SCRIPT` in `src/views/layout.tsx`) opens a hidden `file` input (deliberately **not** `required` — a hidden required control cannot be focused and would block every other submit of the form, e.g. Save profile), and once a file is chosen the form is temporarily retargeted to `POST /dashboard/avatar/upload` and submitted (`form.submit()` ignores `formaction`, so the action is swapped for that one submit). That endpoint stores a magic-byte-sniffed image (PNG/JPEG/GIF/WebP, ≤2 MiB, client-declared MIME ignored) under `avatars/<userId>/<random>.<ext>` with the sniffed content type in `httpMetadata`, then re-saves the stored profile with only `avatar_url` changed (a `/files/…` value — `isSafeUrl` alone would reject it in `POST /dashboard/profile`, which also accepts those paths now). `GET/HEAD /files/*` (`src/routes/files.ts`, mounted before `publicRoutes`; also whitelisted in the maintenance gate) serves only keys matching `STORAGE_KEY_RE`, immutable-cached, conditional GETs via R2 `onlyIf`. Any `avatar_url` change that drops a stored path (profile save, re-upload, admin user delete) best-effort deletes the old object via `deleteStoredImage`. Gallery blocks reuse the same binding: the row's `[data-gallery-upload]` picker is `multiple`, each file goes to `POST /dashboard/gallery-image/upload`, the returned URLs are appended to the row's `items` textarea, and the whole Blocks form is then auto-saved with `fetch` (no manual Save after every image); the textarea remains the source of truth, so the no-JS flow is unchanged.
- **User MFM text is rendered locally**: `src/lib/mfm.ts` (`renderMfm`) wraps `mfm-js` `parse()` and integrates the AST into a **whitelisted HTML string** (all text escaped, links only http/https, `$[...]` args restricted to an allow-list of colors/sizes/positions/animation classes styled in `src/styles/app.css` under the `.mfm-body` wrapper class). It is the single renderer for both MFM surfaces — the bio (`src/views/profile.tsx`) and profile text-block bodies (`src/lib/blocks.tsx`), both via `dangerouslySetInnerHTML` — never widen that integrator without keeping escaping + the URL/color allow-lists intact. mfm-js is a **parser only** (no HTML output), so this module is the only renderer. Note it spells positional args as bare flags (`$[color.red …]` → `{ red: true }`) and includes the leading `@` in `mention.props.acct`.
- Accounts link by verified email across GitHub + magic-link identities (`src/lib/accounts.ts`, `identities` table). **Explicit linking** from the dashboard ("Connected accounts" card) lets either provider be added later: GitHub via `GET /auth/github/link` (OAuth state carries `linkUserId`, callback calls `linkIdentity`) and email via `POST /dashboard/identities/email` (magic link with a KV `link:email:<tokenHash>` intent consumed in `/auth/email/verify`). `linkIdentity` refuses a provider id or verified email already owned by another user; a link intent only applies when the session user matches the one that started it.
- **TOTP login (third sign-in method)**: `src/lib/totp.ts` implements RFC 6238 on Web Crypto (SHA-1 / 6 digits / 30s steps, Base32 secrets — no dependency, no Node crypto). One factor per user lives in the `totp_factors` table; it is unusable until confirmed with a valid code (`confirmed = 0` → pending), and `last_step` stores the newest accepted step so `verifyTotp` rejects replayed or older codes. Setup lives in the dashboard "Connected accounts" card: `POST /dashboard/totp/setup` (stores a pending secret), `/confirm` (code check → enabled), `/disable` (requires a current code; **not** gated on the site toggle so nobody is locked out of removing their factor). Sign-in is `POST /auth/totp` (username/email + code, `totp:ip:`/`totp:id:` KV rate limits, every failure → the same generic `auth.err.totpInvalid` so accounts cannot be enumerated). The login-page form renders only when `settings.totpLoginEnabled` — the admin toggle `totp_login_enabled` (D1 `settings` key, default on), sitting next to `githubLoginEnabled`/`magicLinkEnabled` so all three sign-in methods can be switched independently at `/admin`. The dashboard QR lazily loads `qrcode-generator` from unpkg (same pattern as the profile share card, `TOTP_QR_SCRIPT`) only while a factor is pending, and the `otpauth://` URI + secret are rendered only in that unconfirmed state. Admin user delete also clears `totp_factors`. **The TOTP card is htmx-driven** (`src/views/dashboard.tsx` `TotpCard`, also exported so the routes can render the fragment): the setup/confirm/disable forms carry `hx-post`/`hx-target="#totp-card"`/`hx-swap="outerHTML"`/`hx-scroll="false"` **plus** the native `method`/`action`/`formaction` fallback, so with htmx a key is generated/confirmed/removed by swapping only the `#totp-card` block in place (no full reload, no scroll-to-top), and without JS the plain form POSTs still work. The three `POST /dashboard/totp/*` handlers route their outcome through `totpGoto()` (`src/routes/dashboard.tsx`): when the request has the `HX-Request` header they return the fresh `TotpCard` fragment (inline success/error banner inside the card); otherwise they redirect to `/dashboard/security?saved=`/`?error=` as before. `TOTP_QR_SCRIPT` re-runs on `htmx:afterSwap` (guarded by a `data-totp-rendered` flag) so a freshly generated key renders its QR without a reload.
- **i18n** (`src/i18n/`): `en.ts` is the source-of-truth dictionary; `zh.ts` is typed as `Record<keyof typeof en, string>`, so a key added only to `en` **fails `typecheck`**. Locale resolves cookie `lang` → `Accept-Language` → `en` and is exposed as `c.get('locale')` + translator `c.get('t')` (supports `{name}` interpolation). Views take `t`/`locale`/`pathname` props and set `<html lang>`. Switch via `GET /language/:code?next=…` (sets the cookie), so it must mount before `publicRoutes`.
- **Admin panel** (`/admin`, `src/routes/admin.tsx` + `src/views/admin.tsx`): gated by `requireAdmin` (`src/middleware/auth.ts`). **Every sub-module is its own page** (`/admin`, `/admin/settings`, `/admin/integrations`, `/admin/ai`, `/admin/custom-code`, `/admin/landing`, `/admin/reserved`, `/admin/tags`, `/admin/users`) driven by the registry in `src/lib/admin-nav.ts`, which also feeds the sidebar's second-level menu (a `<details>` submenu in `ConsoleShell`, auto-opened when `pathname` starts with `/admin`) and the overview page's quick links. `renderAdmin(c, section)` loads only the data a section needs, and `AdminView` renders just that section's card; each POST handler redirects back to its own section with `?saved=`/`?err=`. Edits runtime settings (D1 `settings` table, KV-cached via `src/lib/settings.ts`) — display name, **favicon URL** (rendered as `<link rel="icon">` in `src/views/layout.tsx`) and **logo URL** (replaces the default `EO` mark in the nav `Logo`, blank hides it), both validated with `isSafeFaviconUrl`; changing either calls `invalidateAllProfiles` because cached profile HTML embeds them — feature flags, and defaults — plus reserved handles, tag categories, and users (grant/revoke admin, delete → cascades fields/identities/user tags + invalidates cache). Reads `c.get('isAdmin')`; `loadRuntime`'s maintenance gate bypasses admins. New sign-up toggle + default theme/visibility are honored in `src/lib/accounts.ts` / `resolveAccount`.
- **Dashboard sections** (`/dashboard*`, `src/routes/dashboard.tsx` + `src/views/dashboard.tsx`): mirrors the admin pattern — `renderDashboard(c, section)` loads only the data a section needs and renders one card set, driven by the registry in `src/lib/dashboard-nav.ts` (`DASHBOARD_SECTIONS`, display order Profile → Fields → Blocks → Tags → Security → AI) which also feeds the sidebar's second-level `<details>` menu (auto-opened when `pathname` is `/dashboard` or starts with `/dashboard/`). Sections: `/dashboard` (profile form + quick-link cards), `/dashboard/fields`, `/dashboard/blocks` (profile-block editor, see the Profile blocks bullet), `/dashboard/tags`, `/dashboard/security` (connected accounts + TOTP), `/dashboard/ai` (AI status card; config link to `/admin/ai` for admins only). Every form POST redirects back to its owning section with `?saved=`/`?err=`, and account-linking redirects in `src/routes/auth.tsx` target `/dashboard/security`. The AI chat modal + floating button render on **all** sections (the chat is the only entry point, `?ai-open=` on any section works); the modal's `currentAIContext()` null-guards the profile/fields/tags forms, which only exist on their own pages — the server falls back to stored profile data.
- **Global custom code (admin)**: `SiteSettings.customCss`/`customJs`/`customFooter` (D1 keys `custom_css`/`custom_js`/`custom_footer`, 32 KB each) is injected into **every** page by `src/views/layout.tsx` — a `<style data-custom-code>` in `<head>` after `/styles.css` (no nonce: `styleSrc` allows inline), a `<script nonce data-custom-code>` at the end of `<body>`, and a `<footer data-custom-footer>` rendered from **raw HTML** (`dangerouslySetInnerHTML`) that **replaces** the default app-name/tagline footer in `PageShell` and is appended to the main column in `ConsoleShell` (dashboard/admin). CSS/JS content passes through `rawInlineBlock()` (`src/lib/validate.ts`), which only neutralizes `</style`/`</script` (case-insensitive; a raw-text element never decodes entities, so full HTML escaping would corrupt the code); the footer is trusted admin HTML, not escaped. Saved by `POST /admin/custom-code` — **not** `/admin/settings`, which re-saves the whole settings object and must therefore keep `current.customCss`/`customJs`/`customFooter` intact. Any change calls `invalidateAllProfiles()` because cached profile HTML embeds the rendered blocks.
- **`saveSettings()` writes the ENTIRE `SiteSettings`** (whole-object upsert + KV `settings:all` purge). `POST /admin/settings` rebuilds that object from an **explicit per-field list**, so any new `SiteSettings` field must also be added there — otherwise saving the settings form silently drops it. The other writers (`/admin/config/*`, `/admin/ai`, `/admin/custom-code`, `/admin/landing`) spread `{ ...current }` and are safe by default.
- **Landing-page copy (admin)**: the `/` `Home` copy and both CTA targets are admin-overridable, edited as one form via `POST /admin/landing` (**not** `/admin/settings`). `SiteSettings.landingCopy` is a `Record<LandingCopyKey,string>` serialized as JSON in one D1 key `landing_copy` (parsed/clamped by `parseLandingCopy`); the CTA links are separate keys `landing_cta_primary_url`/`landing_cta_secondary_url`, validated by `isSafeLandingUrl` (http(s) / `/path` / `#anchor`). Each text field **falls back to its `home.*` i18n message when blank** (the subtitle also interpolates `{appName}`), and a blank CTA link restores the default button behavior. `/` is **not** profile-cached, so these edits need no `invalidateProfiles` — they propagate via the ~60s `settings` cache.
- **Integrations (GitHub / email / Gravatar) & env locking**: the site name (see `APP_NAME` below), GitHub OAuth credentials, the mailer (`mailer_driver` + `smtp_*`) and the Gravatar mirror are editable in the admin panel and stored in D1 `settings` (secrets in plaintext; secret inputs are never echoed back, so a blank value keeps the stored one). On `/admin/integrations` each module is its own **card with its own form** (GitHub, email, Gravatar), saved independently via `POST /admin/config/{github,email,gravatar}`. `src/lib/config.ts` resolves effective values with **environment variables taking precedence** (`resolveGithub` / `resolveMailer` / `resolveGravatarMirror`), and `envLocks(env)` marks each field whose env var is set. Locked fields render disabled in the admin panel, and the save handlers (`POST /admin/settings` for the site name, `POST /admin/config/*` for the rest) ignore their submitted values, so the console can never override an env var. All `config/*` handlers spread `{ ...current }`, so partial saves never drop unrelated settings. Runtime call sites consume the resolved config — `githubConfigured(config)` / `githubAuthorizeUrl(config, …)` / `exchangeGithubCode(config, …)` and `getMailer(config)` — never `env` directly. In the cards, the secret inputs (`github_client_secret`, `smtp_password`) turn amber and show a "prefer an env var" warning as soon as a value is typed — a pure-CSS effect keyed off `[data-secret-input]:not(:placeholder-shown)` plus the sibling `.secret-warning` rule in `app.css` (which is why those inputs always carry a placeholder).
- **CodeMirror 6 in the admin custom-code card**: bundled locally — `scripts/build-vendor.mjs` uses esbuild to bundle `src/vendor/codemirror.ts` (which re-exports the `@codemirror`/`@lezer` namespaces the admin needs) into `public/vendor/codemirror.js`; there is **no import map and no unpkg request**. `codeMirrorScript(t)` (classic inline script, nonce'd) dynamic-`import()`s `/vendor/codemirror.js` and calls `mountAll` with the namespaces off that module. Rerun `npm run build:vendor` after bumping any `@codemirror`/`@lezer` dependency. The script mounts an `EditorView` into each `[data-cm-editor]` host (keeping the server-rendered textarea in sync via `updateListener` so the form submits the code with or without JS; the textarea gets `data-cm-hidden`, styled offscreen in `app.css`). `css()`/`javascript()`/`html()` return language support **without** highlighting — `syntaxHighlighting()` must be added explicitly. On import failure the plain textareas stay and `[data-cm-status]` shows `admin.code.loadError`. Char counters are `[data-cm-count]` spans index-paired with the hosts (template `admin.code.count` = `{count} / {max}`). Editor chrome lives in `src/styles/app.css` (`.code-source` + `[data-cm-editor] .cm-editor …`). CM injects its base theme *after* this stylesheet at runtime, so at equal specificity CM would win: the `.cm-*` rules are therefore scoped under the `[data-cm-editor]` host to outrank it (only `.cm-selectionBackground` needs `!important` — CM sets that one inline).
- **AI assistant (OpenAI-compatible)**: `src/lib/openai.ts` owns the client. `resolveOpenAI(env, settings)` mirrors the other resolvers (env var wins) and returns `{ client, model }` or `null` when no key is set; a non-empty key is treated as configured — it is **not** validated against the provider. Config (`openaiApiKey`/`openaiBaseUrl`/`openaiModel` + a single system prompt `openaiPromptChat`) lives in D1 `settings` and is edited on its **own admin page** `/admin/ai` (`POST /admin/ai`) with `openaiApiKey`/`openaiBaseUrl`/`openaiModel` env-lockable — the **prompt** field has no env var and is always editable; the secret input is never echoed. Admin `POST /admin/ai/test` only reports whether a key is configured and returns an **HTML fragment** for htmx. The dashboard ships a **chat** modal (`src/views/dashboard.tsx`) that POSTs (with `_csrf`) the message history plus the live (possibly unsaved) form content as `profile` to `POST /dashboard/ai/chat`; the server prepends the system prompt (falling back to `DEFAULT_CHAT_PROMPT`) + that current profile and streams the completion back as **SSE** (`data: {"delta":…}` … `data: {"done":true}`). Each assistant bubble gets a copy button. The client consumes the stream with `fetch` + `ReadableStream` (not `EventSource`, which can't POST or carry the CSRF token). Because CSP has **no `'unsafe-inline'`**, the modal uses `data-ai-*` attributes + one delegated click listener, never `onclick=` (a nonce does not cover inline handler attributes).

## Config / env gotchas
- `wrangler.jsonc` declares D1/KV bindings **without IDs** so Wrangler's Automatic provisioning creates them on `wrangler dev` (local) and on deploy (remote, via the Cloudflare Git integration / Deploy button). Auto-created remote IDs live only in the Dashboard and are **not written back to the repo**. `env.production` **re-declares** `d1_databases` + `kv_namespaces` because bindings are not inherited from the top level; `npm run deploy` runs `wrangler deploy --env production` (Worker `earthol-player-profile-production`).
- Deploy does **not** apply `schema.sql`. After the first deploy, run `wrangler d1 list` to get the auto-created DB name, then `wrangler d1 execute <name> --remote --file=./schema.sql` (or `npm run db:init:remote` if the name matches). `schema.sql` is not idempotent, so apply it only once. **Later schema changes** go in `migrations/NNNN_*.sql` and reach existing DBs with `npm run db:migrate:remote` — never re-run `schema.sql` against a populated database. Migration files **must be re-runnable**: `schema.sql` is applied with `d1 execute`, which never touches the `d1_migrations` ledger, so on a fresh install every migration is still "pending" and WILL be re-executed by the first `wrangler d1 migrations apply`. That is why all of them are built only from `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` (and idempotent `INSERT OR IGNORE` / guarded `UPDATE`), and why 0004 (`profile_block_rules` / `profile_block_viewers`) and 0005 (`profile_layout`) add new *satellite* tables instead of altering existing ones. Never put an `ALTER TABLE` (or a table rebuild to widen a CHECK) in a migration — it cannot be re-run, and it would break every future upgrade on any DB installed from `schema.sql`.
- `APP_URL` builds magic links, canonical URLs, OG tags, and sitemap entries via `appUrl(env)` (`src/lib/env.ts`, default `http://localhost:8787`). `APP_NAME` resolves through `resolveAppName` (`src/lib/settings.ts`), which **prefers the env var over the admin `siteName` setting**, then the built-in default; when `APP_NAME` is set the admin site-name field is env-locked (see the integrations bullet). `wrangler.jsonc` intentionally declares **no `vars`** and sets `keep_vars: true`, so production env vars (including `APP_URL`/`GRAVATAR_MIRROR`) are managed in the Dashboard and survive every deploy. Never re-add `APP_URL`/`GRAVATAR_MIRROR`/`APP_NAME` to `wrangler.jsonc` `vars`: config values win over same-named Dashboard vars, and without `keep_vars` Wrangler deletes Dashboard-only vars on deploy.
- `GRAVATAR_MIRROR` var is the base URL (up to but excluding the hash) for the dashboard's "Use Gravatar" button, e.g. `https://www.gravatar.com/avatar` or a self-hosted mirror like `https://cravatar.cn/avatar`. Resolved via `resolveGravatarMirror` (`src/lib/config.ts`; falls back to the admin setting) and appended to by `src/lib/gravatar.ts`, which still owns the default when both are empty.
- Mailer defaults to the `console` driver (`src/lib/email.ts`): the magic-link URL is printed to the wrangler stdout log. Real sending uses the built-in SMTP client over `cloudflare:sockets` — set `MAILER_DRIVER=smtp` + `SMTP_HOST`/`SMTP_PORT` (465 or 587 only; Workers blocks port 25), `SMTP_SECURE` (`tls` default on 465 / `starttls` otherwise / `none` for local), optional `SMTP_USER`/`SMTP_PASSWORD` (AUTH PLAIN/LOGIN) and `SMTP_FROM`. These can also be set at `/admin/config` (env vars win; see the integrations bullet). Mail failures are caught in `routes/auth.tsx` and rendered as a generic error (never 500).
- GitHub OAuth is optional; the login button is hidden when the client id/secret are unset (env or `/admin/config`). Put local secrets in `.dev.vars` (gitignored), production via `wrangler secret put --env production`.
- Tailwind is v4, CSS-first config in `src/styles/app.css` (no `tailwind.config.js`); class names are auto-detected from source.
- `npm install` may need `npm approve-scripts` for workerd/esbuild; approved packages are listed under `allowScripts` in `package.json`.
- **Admin access**: the **first registered user** is auto-promoted to `users.is_admin=1` by `createUser` (skipped if an admin already exists). `ADMIN_EMAILS` (comma-separated) bootstraps admins — a signed-in user whose email matches is promoted to `users.is_admin=1` by `isAdminUser`. Set it in `.dev.vars` locally, `wrangler secret put`/vars in production.
- **Maintenance mode & feature flags** (sign-ups, magic-link, GitHub login, default theme/visibility) live in the D1 `settings` table, **not** env. Changes propagate via the KV cache within ~60s. During maintenance every request 503s except admins plus `/health`, `/login`, `/auth/*`, `/language/*` — enough for an admin to sign back in and disable it.
